# Kilo mind

The Python side of Kilo (docs/architecture.md §5): the serial link to the body
firmware, the body-state model, the `kilo` CLI, the flash tool and a virtual
body for testing without hardware. Python 3.11+, standard library plus
pyserial at runtime; pytest for the tests.

**Protocol.** The mind speaks the real protocol: `protocol/spec.toml` is the
single source of truth, and the mind uses **vendored copies** of the
generated bindings and the reference codec in `kilo/protocol/`
(`kilo_protocol.py`, generated by `protocol/gen.py`, and `kilo_link_codec.py`,
COBS + CRC-16). They are byte-identical copies made by
`python3 protocol/vendor.py`; never edit them here. After a spec change run
`python3 protocol/gen.py && python3 protocol/vendor.py` and commit the
result; `protocol/test.sh` and `tests/test_codec.py` fail if the copies
drift. Vendoring (rather than importing `protocol/` from the repository)
keeps `kilo` an ordinary installable package. `kilo/link/consts.py` derives
every constant (types, statuses, events, modes, owners, params) from the
generated module; nothing is transcribed from the document.

Link rules (§4): goals are latched and refreshed at 5 Hz with the epoch
current when they were set; any epoch change seen in TELEMETRY, EVENT or HELLO
drops motion goals from older epochs. Queries (HELLO_REQ, PING, STATS_REQ,
PCA_READ, CAL_GET, PARAM_GET, EEPROM_READ) are answered by their data reply
only and retried with a fresh seq; other commands get one ACK and are retried
with the same seq (the body de-dups them for 500 ms). The TX seq starts at a
random value per process. Heartbeats, goal refreshes and HELLO polls (also the
one on connect) are only sent while the mind's main loop proved alive within
1 s.

## Install on the Pi

pyserial comes from apt (`python3-serial`, 3.5). Recommended: a per-repo venv
that can see the system site packages, so pyserial is not installed twice and
the system Python stays untouched:

```sh
sudo apt install python3-serial python3-venv
cd ~/OpenCat
python3 -m venv --system-site-packages ~/OpenCat/.venv
~/OpenCat/.venv/bin/pip install -e mind pytest
echo 'export PATH="$HOME/OpenCat/.venv/bin:$PATH"' >> ~/.bashrc
```

The alternative, `pip install --break-system-packages -e .` into the system
Python, works but mixes pip-managed files into `/usr/local`; prefer the venv.
`pip install -e` makes the source tree live, so `git pull` is enough to update.

Serial access needs the `dialout` group (`sudo usermod -aG dialout $USER`), and
the Pi configuration in docs/architecture.md Appendix F (serial console off,
UART on, 1-Wire off, UART clock 48 MHz, GPIO4 left as an input).

## Port rules

1. `--port P` (or `$KILO_PORT`) always wins.
2. A plugged-in USB serial adapter: the first `/dev/ttyUSB*`, then
   `/dev/ttyACM*` (the Petoi CH340 / CH343 USB adapter, e.g. in WSL2 through
   usbipd, or in one of the Pi's USB ports). Plugging an adapter in is an
   explicit choice, whereas the header UART's device node exists on every Pi
   whether or not anything is wired to it. On a Pi, `kilo` warns that the
   header UART was ignored; select it with `KILO_PORT=/dev/ttyAMA0` (or
   `--port`).
3. Otherwise, on a Raspberry Pi, the header UART: `/dev/serial0` resolved,
   else `/dev/ttyAMA0`. On the Pi 2 B that is the PL011 `ttyAMA0` on
   GPIO14/15.

Device nodes are globbed rather than listed with `serial.tools.list_ports`,
which hides `ttyAMA*`/`ttyS*` as "platform" ports on recent kernels (the same
problem Petoi's `serialMaster/ardSerial.py` works around).

> **Unplug the CH343 USB adapter whenever the Pi drives the UART**, and vice
> versa. Both drive the 328P's single RX line; with both attached, frames from
> each side corrupt the other's. On a Pi with an adapter plugged in, `kilo`
> picks the adapter and prints a warning that the header UART was ignored.

The link runs at 250000 baud 8N1. Flashing uses 115200 (optiboot).

**DTR and resets.** On the NyBoard DTR is AC-coupled to RESET, so a DTR rising
edge (the kernel raises DTR on open) resets the 328P. Every time `kilo` opens a
serial port it clears the tty's HUPCL flag (like `stty -hupcl`), so DTR stays
asserted after close and the next open does not reset the body. `kilo flash`
clears it again right after avrdude, which drops DTR and re-enables HUPCL; the
post-flash verify is then the last reset. The first open after a replug still
resets the body once.

## CLI

```sh
kilo status                  # HELLO, mode, attitude, battery, link stats (--json)
kilo monitor                 # live telemetry table; Ctrl-C to quit
kilo posture stand           # holds the posture until Ctrl-C (or --for SECONDS)
kilo cal [show] | cal set JOINT DEG | cal save | cal revert
kilo param list | param get ID | param set ID VALUE [--persist]   # ID = number or name
kilo pca                     # read back the 16 PCA9685 OFF counts
kilo eeprom dump 0 283       # hex dump of the body EEPROM (EEPROM_READ, 56 B per request)
kilo flash                   # build body/, size harness, reset, avrdude, verify HELLO
kilo flash --no-build        # flash the last build
kilo flash --legacy          # flash mind/firmware/opencat-legacy.hex
kilo vbody                   # virtual body on a pty; prints the pty path
```

Global options: `--port`, `--baud`, `--log` / `--log-file FILE` (JSON-lines
log of every frame and event, written by a background thread),
`--timeout`, `-v`/`-vv`.

There is no daemon yet, so each command opens the port itself. Goals are only
held while the mind is alive: when `kilo posture` exits, heartbeats stop and
the body's watchdog stops motion at 0.5 s and moves to REST at 1.5 s. That is
by design (§4).

### Flashing

`kilo flash` follows Appendix F:

1. `arduino-cli compile --fqbn arduino:avr:uno --output-dir ~/.cache/kilo-build body/`
   with the first 8 hex digits of the git commit as `-DKILO_BUILD=0x...`, then
   `body/tools/size_check.sh --elf` on that build (the size/symbol harness; it
   honours `FLASH_MAX`, e.g. `FLASH_MAX=18432 kilo flash` while the P0 build is
   over its 16 KB ceiling, see docs/architecture.md §8 question 9).
2. Stops the serial link (in-process; a second kilo process cannot hold the port
   because it is opened exclusively).
3. Resets the board: on a USB adapter avrdude toggles DTR itself; on the Pi
   header (`--reset auto` picks it for ttyAMA*/ttyS*/serial0) GPIO4 is driven
   low for 100 ms (`--reset-ms`, spec `reset_pulse_ms`) and released back to an input (emulated
   open-drain, never driven high). The pulse uses the first available of:
   `pinctrl` (raspi-utils, standard on Raspberry Pi OS), the libgpiod tools
   `gpioset`/`gpioget` (apt `gpiod`, v1 or v2), or `/sys/class/gpio`. The
   libgpiod Python bindings are not required.
4. `avrdude -c arduino -p atmega328p -P PORT -b 115200 -D -U flash:w:HEX:i`,
   retried once with a fresh reset. avrdude is taken from PATH or from
   arduino-cli's `~/.arduino15` tools.
5. Clears HUPCL on the port (see "DTR and resets" above), then restarts the
   link and waits up to 3 s for HELLO with reset cause FLASHED
   and, when it built the firmware, `fw_build` equal to that build hash.

`--dry-run` prints the commands without running them.

### Virtual body

```sh
kilo vbody                    # prints e.g. /dev/pts/5; keys: f/F fall, r reboot, q quit
kilo --port /dev/pts/5 monitor
kilo vbody --fall-after 5 --no-keys
```

The virtual body is a Python simulation speaking the real codec and messages.
It implements the P0 body's message-level contract (the same dispatch rules as
the C link layer: ACKs and de-dup, query replies, GOAL_REFUSED reasons,
calibration/params/EEPROM with EEPROM_BUSY, REBOOT, the two-stage watchdog
driven by the WD_* params) plus 25 Hz telemetry with a swaying pitch/roll and
simulated falls. `VirtualBody.process(data, now)` drives it synchronously
(replies are appended to `sent` and written to the transport, if any); a
cross-check test compares it frame by frame with the body's C dispatch. It is
a stand-in for §6's `body/test/vbody`, which will run the real firmware core
on stub HALs.

## Tests

```sh
pip install -e '.[test]'      # or: sudo apt install python3-pytest
python3 -m pytest             # from mind/
```

Everything runs with the real codec and messages. `test_codec.py` checks the
adapters against `protocol/vectors` and that the vendored copies match
`protocol/`. The link tests use an in-memory loopback with a scripted peer:
liveness gating, goal refresh and epoch clearing, query/command retries and
de-dup, reconnect, reboot detection. `test_vbody.py` runs link + client
against the virtual body (every client command) and checks the vbody's
dispatch contract case by case. `test_e2e_cli.py` runs the `kilo` CLI as a
subprocess (`status`, `posture stand`, `param list`, `cal show`) against the
virtual body on a pty. The suite takes about 20 s.

## Layout

```
kilo/protocol/              VENDORED by protocol/vendor.py: kilo_protocol.py, kilo_link_codec.py
kilo/link/codec.py          Codec / Decoder interface and KiloCodec (COBS + CRC)
kilo/link/messages.py       KiloMessages: pack/unpack by name over the generated dataclasses
kilo/link/consts.py         type codes, statuses, events, modes, params (from kilo_protocol)
kilo/link/transport.py      pyserial, raw-fd (pty) and loopback transports
kilo/link/ports.py          port auto-detection
kilo/link/serial_link.py    SerialLink: reader/writer threads, goals, commands
kilo/body/state.py          BodyState
kilo/body/client.py         BodyClient: postures, calibration, params, stats
kilo/log.py                 JSON-lines logger thread
kilo/cli.py                 the `kilo` command
kilo/tools/flash.py         build + flash; kilo/tools/gpio.py GPIO4 reset
kilo/vbody/                 virtual body
firmware/                   stored hex images (legacy firmware)
```
