# Kilo mind

The Python side of Kilo (docs/architecture.md §5): the serial link to the body
firmware, the body-state model, the `kilo` CLI, the flash tool and a virtual
body for testing without hardware. Python 3.11+, standard library plus
pyserial at runtime; pytest for the tests.

**Protocol.** The mind speaks the real protocol: `protocol/spec.toml` is the
single source of truth, and the mind uses **vendored copies** of the
generated bindings and the reference codec in `kilo/protocol/`
(`kilo_protocol.py`, generated by `protocol/gen.py`, and `kilo_link_codec.py`,
COBS + CRC-16). They are byte-identical copies made by
`python3 protocol/vendor.py`; never edit them here. After a spec change run
`python3 protocol/gen.py && python3 protocol/vendor.py` and commit the
result; `protocol/test.sh` and `tests/test_codec.py` fail if the copies
drift. Vendoring (rather than importing `protocol/` from the repository)
keeps `kilo` an ordinary installable package. `kilo/link/consts.py` derives
every constant (types, statuses, events, modes, owners, params) from the
generated module; nothing is transcribed from the document.

Link rules (§4): goals are latched and refreshed at 5 Hz with the epoch
current when they were set; any epoch change seen in TELEMETRY, EVENT or HELLO
drops motion goals from older epochs. Queries (HELLO_REQ, PING, STATS_REQ,
PCA_READ, CAL_GET, PARAM_GET, EEPROM_READ) are answered by their data reply
only and retried with a fresh seq; other commands get one ACK and are retried
with the same seq (the body de-dups them for 500 ms). The TX seq starts at a
random value per process. Heartbeats, goal refreshes and HELLO polls (also the
one on connect) are only sent while the mind's main loop proved alive within
1 s.

## Install on the Pi

The full recipe for the Pi and a dev host is `docs/setup.md`; the essentials:
pyserial comes from apt (`python3-serial`, 3.5). Recommended: a per-repo venv
that can see the system site packages, so pyserial is not installed twice and
the system Python stays untouched:

```sh
sudo apt install python3-serial python3-venv
cd ~/OpenCat
python3 -m venv --system-site-packages ~/OpenCat/.venv
~/OpenCat/.venv/bin/pip install -e mind pytest
echo 'export PATH="$HOME/OpenCat/.venv/bin:$PATH"' >> ~/.bashrc
```

The alternative, `pip install --break-system-packages -e .` into the system
Python, works but mixes pip-managed files into `/usr/local`; prefer the venv.
`pip install -e` makes the source tree live, so `git pull` is enough to update.

Tests: `python -m pytest mind/tests -q`. `-m "not slow"` skips the tests
marked slow (they start `kilo` subprocesses or a daemon and wait in wall
time). `pip install pytest-xdist` and `-n 4` runs the suite in parallel
(sockets, ptys and log directories are per test), but the slow tests then
compete for the CPU and can time out on a loaded machine, so the default run
stays serial. The link and virtual-body timing rules (heartbeat, liveness
window, goal refresh, ACK retries, backoff, the body watchdog) run on a
stepped clock (`kilo.stepclock.StepClock`) and do not depend on load.

Serial access needs the `dialout` group (`sudo usermod -aG dialout $USER`), and
the Pi configuration in docs/architecture.md Appendix F (serial console off,
UART on, 1-Wire off, UART clock 48 MHz, GPIO4 left as an input).

## Port rules

1. `--port P` (or `$KILO_PORT`) always wins.
2. A plugged-in USB serial adapter: the first `/dev/ttyUSB*`, then
   `/dev/ttyACM*` (the Petoi CH340 / CH343 USB adapter, e.g. in WSL2 through
   usbipd, or in one of the Pi's USB ports). Plugging an adapter in is an
   explicit choice, whereas the header UART's device node exists on every Pi
   whether or not anything is wired to it. On a Pi, `kilo` warns that the
   header UART was ignored; select it with `KILO_PORT=/dev/ttyAMA0` (or
   `--port`).
3. Otherwise, on a Raspberry Pi, the header UART: `/dev/serial0` resolved,
   else `/dev/ttyAMA0`. On the Pi 2 B that is the PL011 `ttyAMA0` on
   GPIO14/15.

Device nodes are globbed rather than listed with `serial.tools.list_ports`,
which hides `ttyAMA*`/`ttyS*` as "platform" ports on recent kernels (the same
problem Petoi's Pi-side `ardSerial.py` works around).

> **Unplug the CH343 USB adapter whenever the Pi drives the UART**, and vice
> versa. Both drive the 328P's single RX line; with both attached, frames from
> each side corrupt the other's. On a Pi with an adapter plugged in, `kilo`
> picks the adapter and prints a warning that the header UART was ignored.

The link runs at 250000 baud 8N1. Flashing uses 115200 (optiboot).

**DTR and resets.** On the NyBoard DTR is AC-coupled to RESET, so a DTR rising
edge (the kernel raises DTR on open) resets the 328P. Every time `kilo` opens a
serial port it clears the tty's HUPCL flag (like `stty -hupcl`), so DTR stays
asserted after close and the next open does not reset the body. The first open
after a replug still resets the body once.

After avrdude it takes more than that. Measured on Kilo (2026-10-10): the first
*two* open/close cycles after avrdude each reset the board, and only from the
third does DTR stay up; a port left at B0 (`stty 0`) behaves the same. What we
believe happens: avrdude's arduino programmer ends with DTR and RTS explicitly
cleared, restores its saved termios (HUPCL on) and leaves the line coding at
115200. Several independent things can then make a rising DTR edge on a later
open: the kernel raises DTR on every open whose saved baud is not B0; cdc-acm
raises it when termios goes from B0 to a real baud; HUPCL drops it again on the
last close; and some USB bridges glitch the modem lines on a line-coding (baud)
change. The old sequence fixed these one per open (a raw open that only cleared
HUPCL, then the verify open that set 250000), which gives two resets.

So `kilo flash` now *settles* the port (`kilo.link.transport.settle_port`):
three production opens in a row (pyserial at the link baud, DTR and RTS set
before `open()` so pyserial asserts them, HUPCL cleared, DTR/RTS asserted again,
close, 0.3 s gap). The first makes every transition at once (the one reset
that cannot be avoided: DTR is low after avrdude and must come up); the others
must be no-ops whatever the exact mechanism, and absorb a second reset if there
is one, before the verify opens the port. `kilo -v flash` prints what each
cycle found (HUPCL set or not, DTR/RTS). Tests model the four mechanisms
(`tests/test_settle.py`); the hardware check is docs/p1-hardware-test.md step 2:
`kilo status` right after `kilo flash` must show uptime continuing, not 0.

## CLI

```sh
kilo status                  # HELLO, mode, attitude, battery, link stats (--json)
kilo monitor                 # live telemetry table; Ctrl-C to quit
kilo monitor --rate 25 --json   # JSON lines at 25 Hz (also the default when stdout is not a terminal)
kilo monitor --passive --duration 20   # send nothing; timeline of events and changes
kilo posture stand           # holds the posture until Ctrl-C (or --for SECONDS)
kilo posture stand --for 2 --then-watch 15   # hold, go silent, print the watchdog timeline
kilo posture balance --for 30   # STAND with the balance flag (docs/architecture.md §3f)
kilo balance on --kp 0.6 --kd 0.05 --for 30   # SET_BALANCE gains (live, not persisted) + hold STAND; prints pitch/roll each second
kilo walk --for 5            # trot forward 5 s, then stop (ON THE FLOOR ONLY; see Walking)
kilo walk left --pattern crawl   # turn left in place until Ctrl-C; `kilo walk stop` stops any walk
kilo pose --pitch 5 --posture stance --for 10   # body pose over STANCE and the gait
kilo cal [show] | cal set JOINT DEG | cal save | cal revert
kilo param list | param get ID | param set ID VALUE [--persist]   # ID = number or name
kilo pca                     # read back the 16 PCA9685 OFF counts
kilo eeprom dump 0 283       # hex dump of the body EEPROM (EEPROM_READ, 56 B per request)
kilo flash                   # build body/, size harness, reset, avrdude, verify HELLO
kilo flash --no-build        # flash the last build
kilo flash --legacy          # flash mind/firmware/opencat-legacy.hex
kilo vbody                   # virtual body on a pty; prints the pty path
kilo monitor --percepts      # ... plus percept flags and live percept events (tap, pet, near, startle...)
kilo run [--behaviour] [--remote] [--balance [KP]] [--kilolog]   # the daemon: owns the port, serves the socket (normally systemd)
kilo daemon [status] | daemon stop   # status: port/link state, holds, behaviour, percepts, logs
kilo log summary|replay|plot FILE ...   # log tools (same as python -m kilo.logs; see Logs)
kilo --kilolog status        # any command: raw wire frames to ~/kilo-logs/kilo-<time>.kilolog.gz
```

Global options: `--port`, `--baud`, `--log` / `--log-file FILE` (JSON-lines
log of every frame and event, written by a background thread),
`--kilolog [FILE]` (the raw wire frames, see Logs), `--timeout`,
`-v`/`-vv`, `--socket PATH`, `--direct`, `--override` (through a daemon
running the behaviour runner: pause it while this command holds the body,
see "Behaviour runner and CLI holds").

Every command first tries the daemon's socket and, when no daemon listens,
opens the port itself (the "direct" path, which the hardware-test docs use with
the daemon stopped). Output is the same either way. `--direct` skips the
daemon; `--port P` naming another port than the daemon's opens P directly.

Goals are only held while the mind is alive. Direct: when `kilo posture`
exits, heartbeats stop and the body's watchdog stops motion at 0.5 s and moves
to REST at 1.5 s (§4). Through the daemon the daemon keeps feeding the
watchdog, so it ends the hold itself (see below).

### Walking

**Kilo walks on the floor only, never on a desk or a table** (the owner's
rule: Kilo fell off a desk once). `kilo walk` prints that reminder before
every walk.

```sh
kilo walk [forward|back|left|right|march|stop] [--pattern trot|walk|crawl] [--stride MM] [--turn MM]
          [--period MS] [--duty N] [--step-h MM] [--body-h MM] [--no-bob] [--no-wag] [--no-balance]
          [--for S] [--wait S]
kilo pose [set|release] [--pitch DEG] [--roll DEG] [--height MM] [--xshift MM] [--posture stance] [--for S]
kilo posture stance          # the IK standing posture the gait starts from and hands over to
```

`kilo walk` latches SET_GAIT (run=1, refreshed at 5 Hz with its epoch) and
walks until Ctrl-C, SIGTERM or `--for S`; then it latches the stop (run=0)
and waits for EVENT GAIT_STOPPED (`--wait`, default one period + 1.5 s): the
body ramps the stride down over one period and hands over to STANCE.
`forward` (the default) and `back` use the pattern's stride (`--stride`
sets the magnitude) and `--turn` (+ = left) bends the path; `left` /
`right` turn in place (`--turn` magnitude, default 20 mm; `--stride` makes
it an arc); `march` steps in place. Fields left out take the
docs/architecture.md §3d defaults of the pattern (walk 2000 ms / duty 192 /
30 mm / step 15 mm, trot 1000 / 179 / 35 / 12, crawl 2000 / 218 / 25 / 18);
the body height defaults to 0.8 (crawl 0.7) × (LEG_L1_MM + LEG_L2_MM), read
from the body's params (Kilo's measured legs are the defaults: 45 + 50 mm,
so 76 mm; heights are shoulder axle to the centres of the 6 mm-radius foot
discs, 6 mm less than above the floor). Head bob, tail wag and balance are on unless
`--no-...`. Out-of-range values are refused before anything is sent (the
ranges are the spec's). The body moves to STANCE first from any other
posture; a walk replaces the posture goal (like a trick). The command exits
with status 1 if the body refuses SET_GAIT (printed with a hint: UNKNOWN_TYPE
means a firmware without the gait generator) or an epoch bump (fall,
watchdog, low battery) clears the goal. `kilo walk stop` stops whoever walks
(through the daemon also the IR remote's walk) and waits for GAIT_STOPPED.

`kilo pose` latches SET_BODY_POSE (pitch + = nose down, roll + = right side
up, height delta, forward shift) on top of STANCE and the gait until Ctrl-C
or `--for`, then latches the neutral pose; `kilo pose release` does that at
once. Other postures ignore the pose: `--posture stance` takes STANCE first.

`kilo monitor` shows the gait phase while walking, `kilo daemon` the gait
(pattern, stride, turn, phase, mode), the passive timeline the phase in its
once-a-second line, and `kilo log summary` the time walking, the gait cycles,
GAIT_STOPPED and SET_GAIT refusals.

In Python: `BodyClient.walk(stride_mm=None, turn_mm=0, pattern="trot",
period_ms=None, duty=None, step_h_mm=None, body_h_mm=None, bob=True,
wag=True, balance=True)` (returns the wire fields), `stop_walk(wait_s=None)`
(returns the GAIT_STOPPED count for `wait_gait_stopped(n, timeout)` or, with
`wait_s`, whether it stopped), `await walk_until_stopped(n, timeout)`,
`gait_state()`, `load_geometry()`, `pose(...)`, `release_pose()`. SET_GAIT
run=1 and SET_BODY_POSE are motion goals: stamped with the epoch, cleared on
any epoch change, not sent before contact; a stop (run=0) is never held
back, and GAIT_STOPPED clears it. No behaviour walks yet
(`BodyAdapter.walk` exists): the owner decides when autonomous walking is
allowed.

## Daemon and systemd

`kilo run` is one process that owns the serial port, the `SerialLink` and the
`BodyClient`, and serves a Unix socket. The socket path comes from one
resolver (`kilo.remote.socket_candidates()`) used by both sides: `--socket`,
else `$KILO_SOCKET`, else `/run/kilo/kilo.sock` for root, else
`$XDG_RUNTIME_DIR/kilo/kilo.sock`, then `/run/user/<uid>/kilo/kilo.sock` when
`/run/user/<uid>` exists, then `~/.kilo/kilo.sock`. The daemon listens on the
first; a client without `--socket`/`$KILO_SOCKET` tries them in order and
uses the first daemon that answers. The `/run/user/<uid>` step matters on the
Pi: a non-login SSH shell (`ssh kilo kilo status`) has no `$XDG_RUNTIME_DIR`,
while the systemd user service listens on `/run/user/1000/kilo/kilo.sock`;
before, such a command silently fell back to opening the port directly. The
daemon logs the socket it serves at startup, and `kilo daemon` lists every
path it tried when none answers.

**Port hot-plug.** The daemon starts whether or not the port exists (robot
unplugged, adapter not enumerated yet): `kilo daemon` then shows
`connected=False` and a `link` line (`device MISSING`, the last open error,
the retry period). The link keeps trying to open it, after 2 s and backing
off to every 10 s, so a body plugged in later is picked up within 10 s. A
USB replug makes the next read fail; the daemon closes the port, logs it and
reopens it the same way, and `kilo daemon` counts `reconnects`/`disconnects`.
Every change goes out on the `connection` stream as `{connected, alive, port,
error}`. With `KILO_PORT` (or `--port`) the daemon waits for that exact
node; without, it re-runs the port rules on every attempt. A USB adapter can
come back under another name (`ttyACM1`) if something still holds the old
node; `KILO_PORT=/dev/serial/by-id/usb-...` pins it by serial number.

**Where it is written down.** The daemon is the package `kilo/daemon/`; its
docstrings are the reference and this section only covers running it.
`kilo/daemon/__init__.py`: the module map and the threading rules (what runs
on the asyncio loop, what in the thread pool). `kilo/remote.py`: the wire
format (JSON lines: request, reply, stream). `kilo/daemon/ops.py`: every op
and its arguments, and how requests share the link (one in flight).
`kilo/daemon/sessions.py`: holds, leases, the idle REST/LIMP latch, balance
by default. `kilo/daemon/streams.py`: `subscribe` and the stream kinds.
`kilo/daemon/behaviour.py`: the behaviour runner contract and `--override`.
`kilo/daemon/remote_ir.py`, `port.py` (release for flashing), `logs.py`.

**Protocol.** A failed op comes back as the same exception type the direct
path raises, so the CLI prints the same errors through the daemon as without
it. Ops run in order per client (`trick_play` excepted, so a `trick_stop` or
a disconnect is still seen while a trick plays). The generic `call` op serves
only `look`, `release_head` and `ping` (what `RemoteBody` reaches through its
proxy); goals and tricks have their own ops. The loop never blocks: a client
that does not read loses stream messages (counted, then one `dropped` line)
instead of stalling anyone; one that does not read its replies is
disconnected.

**Holds.** A goal a client sets (`kilo posture`, `kilo balance`, `kilo
walk`, `kilo pose`, a trick) belongs to that client. The daemon keeps it
alive while the client stays connected and sends something at least every
3 s (`RemoteBody` pings while the command holds). When the client goes away,
or goes quiet, the hold ends the way `kilo posture --for` ends without a
daemon, minus the 0.5 s stop stage: the daemon latches REST at once and LIMP
10 s later (`kilo run --idle-posture rest|limp|none`, `--idle-limp S`), a
walk is stopped first (never just dropped), a pose goes back to neutral, and
a balance enable is switched off (or back on with `kilo run --balance`,
below). With a behaviour runner the daemon only drops the goal. The rules for
several clients at once are in `kilo/daemon/sessions.py`.

**Tricks through the daemon.** `kilo trick upload|play|stop` use the trick
ops: the daemon uploads (cached), takes `--posture` first, plays the trick on
its loop and replies on TRICK_DONE. When the `kilo trick play` process exits
or is killed, even mid `--repeats 255`, the daemon stops the trick and runs
the idle REST/LIMP timeline (`kilo daemon` shows `TRICK` in the holds while
it plays). A second client cannot start a trick over a playing one (`kilo
trick stop` first). `kilo trick play --then-watch` needs the port to itself
and is refused through the daemon.

**Behaviour runner and CLI holds.** While `kilo run --behaviour` runs the
behaviour runner, `kilo posture`, `kilo balance`, `kilo walk`, `kilo pose`
and `kilo trick upload|play` through the daemon are refused ("behaviour
runner active; stop it with `kilo daemon stop` ... or pass --override"),
since both would drive the legs. `kilo --override posture stand` pauses the
runner (its running behaviour is halted, a trick it plays stopped, nothing is
ticked) for as long as that command's hold lasts; when the hold ends the
runner resumes and re-asserts its own goals. `kilo trick stop` and `kilo
walk stop` are always allowed.

**Silent modes.** `kilo monitor --passive` and `kilo posture --then-watch`
must send nothing and therefore need the port to themselves; with a daemon on
that port they refuse and say so. Stop the daemon first (`kilo daemon stop`,
or `sudo systemctl stop kilo`).

**Flashing with a daemon.** `kilo flash` builds first, then asks the daemon
to release the port (`release_port`, 300 s lease), runs avrdude, settles the
port, asks the daemon to reacquire it and verifies the HELLO on the daemon's
link. If the flashing client dies (avrdude may still be writing), the daemon
keeps the port released until the lease ends (or `reacquire_port`); every
reopen after a release settles the port first (`kilo/daemon/port.py`). A
daemon without a port yet (nothing plugged in when it started) is still
asked to release, so it does not grab the port mid-flash. Without a
reachable daemon (`--direct`, a daemon of another user, `sudo kilo flash`
while the user service runs) the port's exclusive lock is checked right
before avrdude and a held port is refused (`--force` flashes anyway, with a
warning). As root, `kilo` also looks for the invoking user's daemon at
`/run/user/$SUDO_UID/kilo/kilo.sock`.

**Shutdown.** SIGTERM or SIGINT (or `kilo daemon stop`): stop the behaviour
runner, close clients, drop every goal and go silent so the body's watchdog
takes over (stop, REST, LIMP), close the port, remove the socket.

**Behaviour runner.** `kilo run --behaviour` runs
`kilo.behaviour.runner.run_behaviour` in its own thread with the daemon's
`BodyClient` and its `SharedPercepts` (so the runner and `kilo monitor
--percepts` see the same percepts); the calling contract is in
`kilo/daemon/behaviour.py`. The runner stamps the link's liveness on every
tick; the daemon stamps too, but with a runner only while the runner has
ticked within the last 1 s (10 s of grace for its first tick), so a hung
runner trips the body's watchdog (logged once: "behaviour runner has not
ticked ..."). If the import fails the daemon logs it and runs without. The
packaged runner writes `<log-dir>/behaviour-<time>.jsonl` (see Behaviour)
and stops within 0.1 s of SIGTERM; `$KILO_PERSONALITY` (in
`~/.config/kilo/env`) picks another personality file.

**IR remote.** The body decodes the Petoi IR remote (NEC, on the NyBoard's
receiver at D4) and relays every key as `EVENT IR_KEY` (arg = the NEC
command byte, `| 0x100` for a held-key repeat; HELLO caps bit `IR`). `kilo
monitor` shows it as `IR_KEY 2 (0x18, sit)` (`... repeat` while held), the
passive timeline as `EVENT IR_KEY ...`, and `kilo vbody` sends digits 0-9
from its keyboard. The key table is `kilo.ir.KEYS` (from the legacy
`src/infrared.h`). `kilo run --remote` (off by default, like `--behaviour`;
on the Pi add it to `KILO_RUN_ARGS` in `~/.config/kilo/env`) acts on the
keys through the daemon's own BodyClient:

| Key | Command | Legacy | `--remote` |
|---|---|---|---|
| CH- | 0xA2 | rest | posture rest |
| CH | 0x62 | forward | walk forward (the selected pattern's stride) |
| CH+ | 0xE2 | gyro toggle | balance on/off (SET_BALANCE; Kp from `--balance`, else the default) |
| \|<< | 0x22 | left | turn left in place (turn 20 mm) |
| >>\| | 0x02 | stand | posture stand |
| >\|\| | 0xC2 | right | turn right in place |
| - | 0xE0 | pause/limp | posture limp |
| + | 0xA8 | backward | walk backward |
| EQ | 0x90 | calibrate | ignored |
| 0 | 0x68 | stepping | march in place (stride 0) |
| 100+ | 0x98 | crawl | select crawl |
| 200+ | 0xB0 | walk | select walk |
| 1 | 0x30 | trot | select trot (the default) |
| 2 | 0x18 | sit | posture sit |
| 3 | 0x7A | stretch | trick stretch |
| 4 | 0x10 | hi | trick hi |
| 5 | 0x38 | push-up | trick push_up |
| 6 | 0x5A | pee | trick pee |
| 7 | 0x42 | wash face | trick wash_face |
| 8 | 0x4A | butt-up | trick butt_up |
| 9 | 0x52 | last skill | ignored |

**The direction keys make Kilo walk: use the remote with Kilo on the floor
only, never on a desk.** A direction key walks (SET_GAIT) with the selected
pattern and keeps walking until another key, like the legacy firmware; a
pattern key while walking re-sends the walk with the new pattern (the body
stops and restarts), otherwise it only selects. A posture or trick key
stops the gait first (the stop is latched; the trick takes the legs at
once, a posture is what the body takes after the stop's hand-over to
STANCE); `-` (limp) stops everything at once.
Repeats (a held key) are ignored. A trick key uploads the trick if the body
does not hold it (cached, as `kilo trick play`), stops a playing trick
first, and takes STAND first from LIMP; a posture key also stops a playing
trick. What the remote sets is held like the daemon's idle latch: no idle
REST/LIMP over it, it stays until the next key or a client goal. Keys are
logged and ignored while the behaviour runner is active, while the port is
released for flashing, and while a client holds the posture, a trick or a
walk (the balance key: while a client holds SET_BALANCE; the daemon side is
`kilo/daemon/remote_ir.py`). `kilo daemon` shows `remote on, last key ...`.

**Balance by default.** `kilo run --balance [KP]` (off by default) latches
SET_BALANCE on with the given Kp (default 0.5, the firmware's; 0.99 levels
the whole slope and passed H13 on Kilo) at start, again after a port release
for flashing, and whenever a client's balance hold ends (instead of switching
balance off). Nobody owns it, like the idle latch: Kilo wakes up balancing
whenever it stands or sits, and walks with the gait's balance flag using the
same gains. The body switches balance off on every epoch bump (a fall, the
watchdog, LOW battery, a reboot; P1 finding B1) and the link's 5 Hz refresh
switches it back on within about 200 ms. The remote's CH+ toggles it off and on again with that
Kp; a client's `kilo balance off` holds it off until the client goes away.
`kilo daemon` shows `balance on by default (Kp ...)`. On the Pi:
`KILO_RUN_ARGS=--remote --balance 0.99` in `~/.config/kilo/env` (the owner's choice, 2026-10-11).

**Logs of the daemon.** `kilo run` writes its own log to
`<log-dir>/daemon.log` (`~/kilo-logs/daemon.log`, rotating at 1 MB, 3 old
files kept; `--daemon-log FILE|none`) as well as to stderr, which systemd
sends to the journal; the file is written by a `QueueListener` thread, so a
slow SD card never stalls the link's reader thread, which logs too. `--log`
adds the JSON-lines frame log (64 MB x 6 per start, so it is off unless
asked for: `KILO_RUN_ARGS=--log`) and `--kilolog` the raw `.kilolog.gz`
(both in the log dir). The log dir is kept under 500 MB: at start and hourly
the daemon deletes the oldest kilo logs (`kilo-*`, `behaviour-*`, rotated
`daemon.log.N`) beyond that, never an open file or one written in the last
10 minutes.

**systemd: a system service running as joe.** `mind/systemd/kilo-system.service`,
installed by `sudo mind/systemd/install.sh --system` as
`/etc/systemd/system/kilo.service`, runs `kilo run` as `User=joe`,
`Group=dialout`, with `RuntimeDirectory=kilo`: the socket is
`/run/kilo/kilo.sock` (owned by joe, mode 0660), the first place every
`kilo` command looks, from any shell. Settings stay in
`~/.config/kilo/env` (absolute path written into the unit by install.sh),
so they are edited without sudo and shared with the fallback user unit; the
logs stay in `~/kilo-logs`. Why not the user service it replaces: a user
manager starts only after `systemd-user-sessions.service`, which is ordered
after `network.target`, i.e. after NetworkManager has come up (34 s on the
Pi 2 B), so the daemon started 67 s after power. The system unit has only
the default dependencies (after `basic.target`) and no network or
serial-device ordering (the daemon waits for its port itself): it starts
about 15-20 s after power once the boot is trimmed (docs/setup.md "The daemon as a
system service, and boot time"), and it starts and runs with no network at all (Wi-Fi dongle
unplugged). With no network the only controls are the IR remote
(`--remote`) and the behaviour runner (`--behaviour`), and `~/kilo-logs` is
the only record until the network is back. A daemon started by hand
(`kilo run`) or by the user unit listens in `/run/user/<uid>/kilo` (it
cannot create `/run/kilo`) and refuses to start while another daemon
answers on a socket the clients would find first. The fallback, a *user*
service with lingering (`mind/systemd/kilo.service`, `install.sh` without
`--system`), still works and needs no sudo, but starts a minute late.

### Watching the body on its own (passive)

Every command keeps the body's link watchdog fed while it runs (HELLO_REQ on
connect, heartbeats after 100 ms of silence, the 5 Hz goal refresh), and only
one process can hold the port, so neither `kilo status` nor `kilo monitor`
can watch the watchdog timeline. Two modes send nothing at all:

- `kilo monitor --passive [--duration S]` opens the port and only listens.
  The body needs nothing from the mind for its streams: TELEMETRY flows from
  boot at the TELEM_DIV rate (25 Hz), and EVENTs and the boot HELLO are sent
  unprompted. Not a single byte is written, so the watchdog is not fed and,
  on a body nobody has talked to since boot, not even armed. Opening the port
  can still reset the body over DTR (see "DTR and resets").
- `kilo posture P --for S --then-watch T` holds P for S seconds, then stops
  writing at once (`SerialLink.go_silent()`: latched goals and queued frames
  are dropped, no final refresh, every later write is refused under the TX
  lock) and prints the same timeline for T seconds. It prints the host time of
  the last frame and the last HEARTBEAT it sent; t=0 is the last frame, which
  is when the watchdog was last fed.

Timeline lines carry seconds since t=0 at 0.1 s resolution: every EVENT, each
change of TELEMETRY mode, epoch, owners and flags (DIST_FRESH and OVERRUN
flicker and are left out), and a telemetry summary every second. The watchdog
from a held STAND reads (on the virtual body with `WD_LIMP_S` 1):

```
silent: last frame HEARTBEAT sent at 18:44:39.249 (t=0), last HEARTBEAT at 18:44:39.249 (t=+0.00); watching 3.5 s
   +0.0s  state: mode IDLE  epoch 0  owners IDLE/IDLE  flags link_ok,servos_powered
   +0.5s  EVENT WATCHDOG arg=0 tick=68 epoch=1
   +0.5s  mode IDLE -> LINK_LOST  (watchdog stage 1: stop)
   +0.5s  epoch 0 -> 1
   +0.5s  flags -link_ok
   +1.5s  owners IDLE/IDLE -> REFLEX/REFLEX  (reflex took over: watchdog REST)
   +2.5s  flags -servos_powered  (servos off: LIMP)
```

The mode stays LINK_LOST through REST and LIMP (the body reports LINK_LOST
while any watchdog stage is active); REST shows as the REFLEX owner, LIMP as
`servos_powered` going away. On the real body LIMP comes `WD_LIMP_S` after the
1 s REST move ends (1.5 + 1 + 10 = 12.5 s by default); the virtual body
starts the LIMP timer at the REST trip (11.5 s).

### Flashing

`kilo flash` follows Appendix F:

1. `arduino-cli compile --fqbn arduino:avr:uno --output-dir ~/.cache/kilo-build body/`
   with the size flags (`-mcall-prologues` in `compiler.cpp.extra_flags` and
   `compiler.c.extra_flags`, `-Wl,--relax` in `compiler.c.elf.extra_flags`;
   docs/architecture.md §3h) and the first 8 hex digits of the git commit as
   `-DKILO_BUILD=0x...` (also in `compiler.cpp.extra_flags`), then
   `body/tools/size_check.sh --elf` on that build (the size/symbol harness; it
   honours `FLASH_MAX`, e.g. `FLASH_MAX=18432 kilo flash` while the P0 build is
   over its 16 KB ceiling, see docs/architecture.md §8 question 9).
2. Releases the port: asks a running daemon to let go of it (see "Daemon and
   systemd"), or stops its own link. A second kilo process cannot hold the
   port meanwhile because it is opened exclusively.
3. Resets the board: on a USB adapter avrdude toggles DTR itself; on the Pi
   header (`--reset auto` picks it for ttyAMA*/ttyS*/serial0) GPIO4 is driven
   low for 100 ms (`--reset-ms`, spec `reset_pulse_ms`) and released back to an input (emulated
   open-drain, never driven high). The pulse uses the first available of:
   `pinctrl` (raspi-utils, standard on Raspberry Pi OS), the libgpiod tools
   `gpioset`/`gpioget` (apt `gpiod`, v1 or v2), or `/sys/class/gpio`. The
   libgpiod Python bindings are not required.
4. `avrdude -c arduino -p atmega328p -P PORT -b 115200 -D -U flash:w:HEX:i`,
   retried once with a fresh reset. avrdude is taken from PATH or from
   arduino-cli's `~/.arduino15` tools.
5. Settles the port (three production open/close cycles, see "DTR and
   resets" above; `--settle-cycles N`), then restarts the link (or has the
   daemon reacquire the port) and waits up to `--verify-timeout` (8 s) for a
   HELLO received after the flash: reset cause FLASHED on the Pi header UART,
   any cause over a USB adapter (where the settle reset makes it
   WARM_UNEXPECTED), and, when it built the firmware, `fw_build` equal to that
   build hash. On Kilo reset, optiboot's wait, DMP init and the first HELLO
   take about 2.2 s, plus the link restart; if the boot HELLO went out before
   the port was open it asks with HELLO_REQ. Either way it prints the HELLO it
   saw (build and reset cause), and on failure the last one, if any. A failed
   verify is retried once (`verifying once more`); if it fails again `kilo
   flash` prints `verify FAILED: ...` and exits 1.

Exit codes: 0 flashed (and verified, unless `--no-verify`/`--legacy`), 1 a
build, avrdude or port error, a busy port (without `--force`) or a failed
verify, 2 usage.

`--dry-run` prints the commands without running them.

### Virtual body

```sh
kilo vbody                    # prints e.g. /dev/pts/5; keys: f/F fall, r reboot, q quit
kilo --port /dev/pts/5 monitor
kilo vbody --fall-after 5 --no-keys
```

The virtual body is a Python simulation speaking the real codec and messages.
It implements the P0 body's message-level contract (the same dispatch rules as
the C link layer: ACKs and de-dup, query replies, GOAL_REFUSED reasons,
calibration/params/EEPROM with EEPROM_BUSY, REBOOT, the two-stage watchdog
driven by the WD_* params) plus 25 Hz telemetry with a swaying pitch/roll and
simulated falls, the P1 tricks, balance and head hold, and (P2) the gait's
state machine: SET_GAIT with the body's refusals (BAD_ARG from the spec
ranges; a stop is never stale; STALE, FALLEN, LOW_BATT, UNCALIBRATED), STANCE
first, mode/flag/owner GAIT, `gait_phase` advancing 65536·20/period_ms per
tick, a one-period ramp-down to STANCE with one EVENT GAIT_STOPPED, an epoch
bump or LIMP ending it at once, a trick taking the legs while the gait
continues underneath, SET_BODY_POSE tilting the reported attitude, and a
JOINTS stream of fake angles that swing with the phase. The full contract is
the docstring of `kilo/vbody/sim.py`; `VirtualBody(p2=False)` plays the P1
body (SET_GAIT/SET_BODY_POSE UNKNOWN_TYPE, STANCE BAD_ARG), which the
cross-check uses against a firmware without the gait. `VirtualBody.process(data, now)` drives it synchronously
(replies are appended to `sent` and written to the transport, if any); a
cross-check test compares it frame by frame with the body's C dispatch. It is
a stand-in for the real firmware core, which `kilo/vbody/core.py` runs as a
virtual body (`body/test/core_harness.cpp` on host fakes; `python -m
kilo.vbody.core` serves it on a pty, `tests/test_corebody.py` drives it in
lockstep); the differences found between the two are listed in that test.

## Tricks

`kilo/tricks/` holds the trick model, the importer for the legacy skill
tables, the first-version library and the player timing model
(architecture §3e, §5). `BodyClient` uploads and plays them and `kilo trick`
drives that from the CLI (below).

**Model** (`model.py`). A `Keyframe` has 16 joint slots in degrees (legacy
numbering; `None` = not driven, sent as −128 "unchanged"; slots 3-7 are never
driven), `dur` (ticks from the previous frame, 1..255), `hold` (ticks after
arriving), `easing` (linear, cosine, step), a `balance` bit and an optional
legacy IMU `trigger` (metadata only: the body has no triggers and validation
rejects it). A `Trick` has the frames, `loop_start`/`loop_end` (inclusive) and
`repeats`, expected roll/pitch, the `BALANCE`/`FALL_OK` flags and
`end_posture`; `joint_mask` is derived from the joints any frame drives.

- `mirror()` is the legacy `Skill::mirror()` rule: negate head pan and tail,
  swap the L/R pairs (8,9) (10,11) (12,13) (14,15), negate the expected roll.
  Head tilt is unchanged. It is an involution.
- `speed(f)` plays `f` times faster: `dur` and `hold` are divided by `f`
  (`dur` ≥ 1; a result over 255 raises).
- `validate()` / `problems()`: 1..24 frames (`TRICK_CAPACITY`), `dur`/`hold` in range, loop inside
  the frames, angles within the joint limits of `body/src/core/joints.cpp`
  (a test cross-checks the table), no driven unused slot, no trigger.
- Wire: `Keyframe.encode()`/`decode()` are the 14 B frame of
  `protocol/spec.toml` via the generated `kilo_protocol.Keyframe`;
  `Trick.upload_messages(trick_id)` gives `TRICK_BEGIN`, the `TRICK_FRAMES`
  chunks (4 frames each) and `TRICK_COMMIT` with the CRC-16 of the frame
  array; `Trick.from_wire()` rebuilds a trick. `TRICK_BEGIN` also carries the
  expected roll/pitch in whole degrees (the balance reference for frames with
  the balance bit). Angles are rounded half away from zero. On the body −128
  ("unchanged") becomes the previous frame's angle by index; in frame 0 it is
  the joint's pose when the trick started.
- `repeats` follows the legacy `loopCycle[2]`: the loop section is played
  `repeats` times in total, 0 and 1 both mean once, 255 until stopped.

**Playing** (`kilo/body/client.py`, `kilo/tricks/player.py`, `kilo/cli_trick.py`).

- `client.upload_trick(trick)` returns `(trick_id, uploaded)`. The body holds
  one trick; `trick_id` is a 1..254 tag derived from the header and frames.
  Cached: if this client committed it (no reboot since) nothing is sent;
  otherwise `TRICK_COMMIT` alone asks the body (OK = it holds exactly this
  trick; the body checks the CRC it computed while the frames arrived), and
  only then the full upload goes out.
- `await client.play(name_or_trick, mirror=False, speed=1.0)` uploads if
  needed, releases the latched posture goal (the trick's end posture replaces
  it), sends `TRICK_PLAY` (speed and mirror are applied by the body, so one
  upload serves every variant) and resolves on `EVENT TRICK_DONE` with a
  `TrickResult(reason, trick_id, elapsed_s, expected_ticks, epoch)`; reason is
  DONE, STOPPED, PREEMPTED or FELL. Timeout: the expected duration plus 1 s
  (none for `repeats` 255); on timeout it sends `TRICK_STOP` and raises.
  A refusal is a `CommandError` (BUSY from LIMP, CALIB, under a reflex or
  while playing; STALE; LOW_BATT; UNCALIBRATED). `client.stop_trick()` stops.
- `kilo.tricks.player` is the body's player timing in Python: a phase of n
  ticks takes ceil(n · 64 / speed_q6) ticks; TRICK_DONE comes the tick after
  the last phase. The vbody plays with it, so its TRICK_DONE lands on the
  body's tick (checked by `tests/test_crosscheck.py`).
- CLI: `kilo trick list`, `kilo trick show NAME` (no body needed), `kilo
  trick upload NAME [--force]`, `kilo trick play NAME [--mirror] [--speed X]
  [--repeats N] [--for S] [--posture stand] [--then-watch T]`, `kilo trick
  stop`. A trick cannot start from LIMP: `--posture stand` first.

**Head (P1, architecture §3c layer 1).** `client.look(pan_deg, tilt_deg,
tail_deg=None, speed_dps=120)` latches `SET_HEAD` mode HOLD (refreshed at
5 Hz, epoch-stamped, dropped on an epoch change like every motion goal; the
tail is sent as −32768, "not held", unless given; `speed_dps=0` leaves only
the body's 500°/s safety slew). The body holds the head while its owner is
IDLE or GAIT, without balance corrections, and lets go after 2 s without a
refresh, on an epoch bump, or on `client.release_head()` (clears the goal
and sends mode RELEASE once). TELEMETRY shows head owner `PI_HOLD` and the
`head_held` flag. CLI: `kilo look PAN TILT [--tail T] [--speed DPS] [--for S]
[--posture stand]`, which releases the head when it ends.

**Fall (P1, architecture §3g).** The body's fall reflex sends `FELL` (±1 roll,
±2 pitch) with a new epoch (the link clears the motion goals), plays the
legacy `rc` itself and ends with `RECOVERED` (it then stands) or
`RECOVERY_FAILED` (REST, then LIMP). Meanwhile current goals are refused
`FALLEN` (`TRICK_PLAY`: `REFUSED_FALLEN`); only `SET_POSTURE LIMP` ends the
reflex. The vbody's `trigger_fall(side)` mimics the events and refusals
with a fixed 1 s + 1 s timeline.

**Library layout.** One JSON file per trick in `kilo/tricks/library/`, named by
the Kilo name. JSON because §5 specifies JSON keyframes, it is in the stdlib
(TOML has no stdlib writer), and the files are generated anyway. Each file
records `source` (legacy file, array name, kind, period, angle ratio, loop
bytes), `notes` (every mapping decision and any clamping or dropped data),
`expected` roll/pitch, `loop`, flags, `end_posture` and one line per frame
with joints by name (`head_pan`, `head_tilt`, `tail`, `lf_shoulder`,
`rf_shoulder`, `rb_shoulder`, `lb_shoulder`, `lf_knee`, ...). `library.load()`
accepts the Kilo name or the legacy token.

| Kilo name | legacy | kind | frames | loop (start, end, repeats) | end posture |
|---|---|---|---|---|---|
| sit | `sit` | posture | 1 | - | SIT |
| rest | `rest` | posture | 1 | - | REST |
| stand | `up` | posture | 1 | - | STAND |
| stretch | `str` | posture | 1 | - | STAND |
| balance | `balance` | posture | 1 | - | STAND |
| hi | `hi` | behaviour | 6 | 2, 3, 3 | STAND |
| wash_face | `wsf` | behaviour | 6 | 2, 3, 3 | SIT |
| check_around | `ck` | behaviour | 3 | 0, 1, 2 | STAND |
| sniff | `snf` | behaviour | 5 | 2, 3, 3 | STAND |
| scratch | `scrh` | behaviour | 6 | 3, 4, 5 | STAND |
| pee | `pee` | behaviour | 5 | 2, 3, 2 | STAND |
| push_up | `pu` | behaviour | 6 | 1, 2, 3 | STAND |
| butt_up | `buttUp` | posture | 1 | - | STAND |

**Importer.** `python -m kilo.tricks.import_legacy` (from `mind/`) parses
`src/InstinctNybble.h` with `legacy.py` and rewrites the library; it is
idempotent, and `--check` only reports stale files (a test does the same).
`legacy.parse_file()`/`parse_text()` read any file in the same format and
return the raw arrays (`LegacySkill`), which `legacy.to_trick()` maps:

- Legacy layout: header `period, roll, pitch, angle_ratio` (+ `loop_start,
  loop_end, cycles` when `period < 0`), then `|period|` rows: postures
  (`period == 1`) 16 angles; gaits (`period > 1`) 8 angles for joints 8-15;
  behaviours (`period < 0`) 16 angles + `speed, delay, trigger axis, trigger
  angle`. `angle_ratio` 2 means angles are stored halved (none in Nybble).
- **speed → dur.** Legacy `transform()` moves at `speed/4` degrees per step
  in `round(maxΔ / (speed/4))` steps, one PCA write per joint per step, cosine
  eased. `dur = ceil(steps · LEGACY_STEP_MS / 20 ms)` with `LEGACY_STEP_MS =
  5.5` (est., to be calibrated by filming `hi` on both firmwares); `maxΔ` is
  over the 11 driven joints from the previous frame, and frame 0 is sized
  from the `up` posture. `speed ≤ 0` (legacy "jump") → `dur 1`, step easing.
- **delay → hold.** Legacy waits `|delay| · 50 ms`, so `hold = round(|delay| ·
  2.5)` ticks (half up).
- Postures: `dur 25` (the body's default posture transition; legacy moves
  from wherever it is at 2°/step), balance on. Gaits: 1 tick per frame
  (est.), linear, legs only, loop until stopped. Behaviours: balance off
  (legacy never balances during a behaviour).
- Joints 3-7 are dropped; angles beyond the joint limits are clamped (legacy
  clamps too in `calibratedPWM()`). Six of the thirteen are affected: `sit`,
  `hi`, `wsf` and `scrh` ask up to −90° of the back shoulders, `buttUp` 90°
  of the front shoulders (`wsf` 87° of LF), `str` 70° of the head tilt
  (limit 45°). Each file's
  `notes` names the clamped joints.
- `end_posture`: behaviours take the nearest built-in posture (`up`, `sit`,
  `rest`) by leg angles; posture tricks their own if they are one, else STAND.
  `FALL_OK` is set when the expected tilt exceeds 45° (none of the list).

## Perception

`kilo/perception/` turns TELEMETRY into percepts for the behaviour layer
(§5 "Perception"). Pure Python, no threads; numpy is optional (the 10 s
ring buffer uses it when `python3-numpy` is installed, `array` otherwise).

```python
from kilo.perception import Percepts
pc = Percepts()
p = pc.update(link.state)        # a BodyState, a snapshot() dict, a TELEMETRY message...
p["near"], p["approaching"], p["approach_mm_s"], p["tilted"], p["picked_up"], p["tap"], p["pet"]
for e in p["events"]: ...        # PerceptEvent(t, name, data) produced by this update
pc.notify_self_motion(seconds=1.0)  # when the mind starts a posture move
```

Attitude convention as measured on Kilo: nose **down** = +pitch, **right**
side up = +roll, degrees (the spec.toml field comments say the opposite).

- **Ultrasonic** (`ultrasonic.py`, fed once per `DIST_FRESH` range, 12.5 Hz):
  median of the last 3 echoes (≤ 0.5 s old), range rate by least squares over
  0.8 s (a jump > 200 mm restarts the window, so a walk-by is not an
  approach). `near` < 150 mm (left > 200), `clear` > 400 mm (left < 350) or no
  echo for 1 s, each confirmed by 2 samples; `approaching` when the range
  closes faster than 100 mm/s for 3 samples within 2 m (released above
  −40 mm/s), cooldown 2 s. Single dropouts and spikes change nothing.
- **IMU** (`imu.py`): `tilted`/`level` (> 25° from the posture's reference
  for 0.5 s, released < 18°; the reference is set by the caller or learned
  once calm after a mode change), `picked_up`/`put_down` (≥ 12° of attitude
  excursion within 1 s for 0.5 s, 6° with servos off, while the body is not
  moving itself), `tap` (1.5°+ impulse on a still body, rising within
  0.12 s, gone within 0.35 s), `pet` (gentle 1.5-10° rocking, ≥ 4 half
  cycles of 0.2-1.5 s in 4 s, never faster than 30°/s), `startle` (≥ 10°
  within 0.2 s, or a gyro rate ≥ 250°/s). Each has a cooldown. During GAIT,
  TRICK, RECOVERING and for 1 s after a mode change only `tilted` runs.
  Tap/pet/startle need ≥ 10 Hz telemetry, pickup ≥ 5 Hz.
- **Limits.** Telemetry has attitude and gyro but no accelerometer, so a
  straight lift or being held still in the air is invisible; pickup is an
  attitude-motion heuristic. Raw accelerations (or at least |a| − 1 g), a
  per-tick max gyro rate since the last telemetry, and the posture id would
  make pickup, tap and the reference much better.

All thresholds are fields of `UltrasonicConfig` and `ImuConfig`.

`SharedPercepts` (`shared.py`) wraps one `Percepts` in a lock for several
threads: the daemon feeds it on every TELEMETRY, the behaviour runner calls
`update(state)` each tick and `notify_self_motion()` before each move it
starts (a sample already seen is skipped, so nothing is counted twice).
`kilo monitor --percepts` shows the flags in the table (or a `percepts` list
in each JSON line) and prints each percept event as it happens
(`{"time": ..., "percept": "tap", ...}` in JSON mode); direct it runs its own
`SharedPercepts`, through the daemon it reads the daemon's (`percepts` op and
stream).

## Logs

`kilo --log` (or `--log-file F`) writes JSON lines (`kilo/log.py`): `rx`/`tx`
records with the frame type, seq, payload hex and decoded `fields`, plus
`event`, `link`, `goal`, `cmd`, `rx_error`. `kilo/logs/` reads those, the
1 Hz JSON lines that `kilo monitor` prints when stdout is not a terminal, and
the raw `.kilolog` format below:

```sh
kilo log summary ~/kilo-logs/kilo-20261010-213000.jsonl [--json]
kilo log replay FILE [--json] [--with-body-events]   # percept events the log would produce
kilo log plot FILE --fields pitch,roll,dist,batt [--out x.png|x.csv] [--csv]
```

(`kilo log ...` is `python -m kilo.logs ...`.)

`summary` gives duration, telemetry rate, tick gaps, pitch/roll/gyro stats,
battery, distance echo rate, the mode timeline and the body's events.
`plot` writes a PNG with matplotlib (`sudo apt install python3-matplotlib`)
and a CSV otherwise. Field names: `pitch roll rate_pitch rate_roll rate_yaw
dist batt load mode balance tick epoch rx_err`. There is no `corr`:
balance corrections are not in TELEMETRY.

**`.kilolog`** (`kilo/logs/kilolog.py`): `b"KILOLOG\n"`, a u16-length JSON
header (version, proto, start times, tick_hz), then per frame
`u8 dir | u32 t_ms | u8 n | n bytes` of the wire frame as sent (COBS +
0x00). ≈3.5 MB/h of 25 Hz telemetry, ≈1 MB/h as `.kilolog.gz` (read and
written transparently). `kilo --kilolog [FILE] COMMAND` (direct) and `kilo run
--kilolog [FILE]` (the daemon; flushed every 5 s, so a killed daemon leaves a
readable file) hand a `KilologWriter` to the link, which calls `write_wire()`
for every frame it writes and every frame its decoder completes (the
decoder's `feed_wire()` returns each frame with its wire bytes).
`write_wire()` only queues the record (bounded; when full, records are
dropped and counted in `dropped`): a `kilo-kilolog` thread does the writes,
the gzip flushes and the close, so the link's reader and writer threads (the
writer holds its TX lock) never wait for the disk. The default
file is `~/kilo-logs/kilo-<time>.kilolog.gz` (the daemon: in `--log-dir`).
Through a daemon, `kilo --kilolog CMD` notes that the daemon does the logging.

## Behaviour

`kilo/behaviour/` is the P3 mind (§5): a small behaviour-tree engine under a
utility selector driven by four drives, tuned by an editable personality file.
It is ticked at 10 Hz by an asyncio runner that writes a JSONL behaviour log.

**Engine** (`tree.py`). Nodes return RUNNING, SUCCESS or FAILURE from
`tick(ctx)` and are `halt()`ed (resetting them, cancelling a coroutine) when a
parent abandons them. `Sequence` keeps its place (`memory=False` makes it
reactive, re-checking leading conditions as guards); `Selector` is
memory-less, re-checking from the first child every tick, so a higher branch
preempts and halts a lower running one; `Parallel` has policies `all` and
`any`. Decorators: `Cooldown(s)`, `Timeout(s)`, `Chance(p)` (rolled once per
run on the seeded RNG), `Inverter`, `Repeat(n|forever)`, `ForceSuccess`.
Leaves: `Action` (a function returning a status/bool/None, or a coroutine,
which runs as a task and keeps the node RUNNING until done), `Condition`,
`Wait(s)`. The `Context` carries the injectable clock, the body, the latest
`BodyState.snapshot()`, percepts, drives, the RNG and scratch data, and
records each tick's active path (node names down to the running leaf).

**Drives** (`drives.py`), all in [0, 1]: *energy* drains while active (slowly
while still) and recovers while napping, capped by the battery (no cap above
`battery_full_pct`, zero at `battery_empty_pct`); *curiosity* grows unless
exploring; *sociability* grows while alone and drops while a face is seen or
Kilo is petted; *arousal* spikes on a startle (a fall, a fast approach) and
halves every `half_life_s`.

**Selector** (`selector.py`). Safety branches first, in order: *fallen* (wait
for the body's own recovery, then `fallen_settle_s`), *wind_down* (critical
battery, a CRITICAL `LOW_BATTERY` event or a shutdown request: sad beep, rest,
wait `wind_down_s`, then ask for poweroff; latched), *low_battery* (balance
off, rest, until the battery is 5 % above the threshold). Otherwise each
behaviour scores `sum(weight × term) + noise`, where terms are the drives,
`fatigue` (1 − energy), `calm` (1 − arousal), percepts as 0/1 (`face`, `pet`,
`near`, `approaching`, `alone`), `base` (1) and products such as
`sociability*face`; the noise is a per-behaviour uniform offset redrawn every
`noise_period_s`. Hysteresis: a challenger must beat the running behaviour by
`margin`, after `min_dwell_s` (nap: `min_s`); `urgent` behaviours skip the
dwell; when a behaviour finishes, the best is taken freely; if the choice
FAILs (greet on cooldown), the current one and then the rest are tried in the
same tick.

**Behaviours** (`library.py`): *idle* (sit; every few seconds maybe glance
around), *explore* (a stub until gaits exist: stand and look around N times),
*nap* (balance off, rest, head down), *greet* (when a face or petting is
present: stand, look at it, `play("hi")`; cooldown), *startle* (stand with
balance, look toward the stimulus, hold). They call a duck-typed body:
`posture(name, balance=None)`, `set_balance(enable)`, `look(pan, tilt)`,
`play(trick, mirror=False)` (awaitable) and `beep(notes)`. `BodyAdapter`
(`adapter.py`) maps these onto `BodyClient`; head, tricks and the buzzer are
not in the body yet, so it stubs them (counted in `adapter.unsupported`).
Postures are sent on change only and re-asserted after an epoch change.

**Personality** (`personality.yaml`, loaded by `personality.load(path)`):

| Section | Keys |
|---|---|
| `drives` | `initial.{energy,curiosity,sociability,arousal}`; `energy.{drain_active,drain_idle,recover_rest,battery_full_pct,battery_empty_pct}`; `curiosity.{growth,satisfy}`; `sociability.{growth,satisfy}`; `arousal.{startle,approach,half_life_s}`; `noise` |
| `weights` | per behaviour (`idle`, `explore`, `nap`, `greet`, `startle`): `term: weight` |
| `selector` | `noise`, `noise_period_s`, `margin`, `min_dwell_s`, `urgent` |
| `safety` | `low_battery_pct`, `critical_battery_pct`, `wind_down_s`, `fallen_settle_s` |
| `percepts` | `near_mm`, `approach_mm_s` (ultrasonic) |
| `behaviours` | `idle.{posture,look_every_s,look_chance,look_pan_deg,look_tilt_deg}`, `explore.{posture,look_every_s,looks,look_pan_deg,look_tilt_deg}`, `nap.{posture,min_s}`, `greet.{trick,cooldown_s}`, `startle.hold_s` |

Every key is optional (defaults in `personality.py`, equal to the packaged
file); a behaviour's `weights` replace the default ones as a whole. Unknown
keys, unknown terms, wrong types and out-of-range values are errors naming the
key. PyYAML is optional (`pip install -e '.[behaviour]'` or apt
`python3-yaml`); without it a built-in parser reads the subset the file uses
(block mappings, `- ` lists, one-line `{}`/`[]`, comments, scalars).

**Running it.**

```sh
python3 -m kilo.behaviour --vbody --seconds 120 -v       # in-process virtual body
kilo vbody &                                              # or on a pty ...
python3 -m kilo.behaviour --port /dev/pts/5 --personality my.yaml --seed 7
```

Ctrl-C stops; SIGTERM asks for the wind-down. `--poweroff-cmd 'sudo systemctl
poweroff'` is run when the wind-down completes (nothing is powered off
otherwise). In code: `Runner(body, cfg, percepts=fn, clock=..., sleep=...,
seed=..., log_path=...)` then `await runner.run(duration)`; `stop()` and
`request_shutdown()` end it. `percepts()` returns a dict (`face`, `face_pan`,
`pet`, `startle`, `stimulus_pan`, `shutdown`, `battery_critical`); `near` and
`approaching` come from the snapshot's ultrasonic fields (personality
`percepts` thresholds) unless the source provides them.

**Under the daemon** (`kilo run --behaviour`): `run_behaviour(client,
state, stop_event, log_dir)` builds `BodyAdapter(client, percepts=...)` and a
`PerceptFeed` that calls `Percepts.update(state)` each tick and maps the
result to the behaviour percepts the selector terms read. `python -m
kilo.behaviour` uses the same feed. The mapping:

| behaviour percept | from `Percepts` | used by |
|---|---|---|
| `face` | always False (no camera yet) | terms `face`, `alone`; greet |
| `pet` | `pet` (gentle rocking) | terms `pet`, `alone`; greet; sociability |
| `near` | `near` (< 150 mm, hysteresis) | term `near` |
| `approaching` | `approaching` (closing > 100 mm/s) | term `approaching`; arousal |
| `alone` | derived by the selector: not (`face` or `pet`) | term `alone` |
| `startle` | 1.0 while `startle` is held (1 s), or on a new fall | arousal; startle |
| `tap`, `tilted`, `picked_up`, `clear` | the flags of the same name | log only (no term yet) |
| `percept_events` | names of this tick's PerceptEvents | log |

The adapter calls `notify_self_motion()` before every posture change (0.5 s),
head look and trick it starts, so Kilo's own moves are not read as a tap or
a pickup. Body events: the runner has no BodyClient callback yet, so
`BodyEvents` (`body_events.py`) diffs successive snapshots (epoch, the last
8 EVENTs, connected/alive) and the runner logs `body_event` records (epoch
change, FELL, WATCHDOG, LOW_BATTERY, BOOT, LINK_RESTORED, connection) and
calls `on_body_event`.

**Behaviour log**: `~/kilo-logs/behaviour-YYYYmmdd-HHMMSS.jsonl` by default,
written by `kilo.log.JsonlLogger` (queue + writer thread, never blocking the
loop). A `start` record (`seed`, `hz`, `personality`), then `behaviour`
records whenever the choice or the active path changes and at least once a
second:

```json
{"t": 1234.5, "wall": 1791692517.47, "kind": "behaviour", "tick": 101,
 "chosen": "idle", "reason": "best", "status": "running",
 "path": ["root", "idle", "idle_seq", "Forever", "idle_beat", "Wait(6s)"],
 "drives": {"energy": 0.79, "curiosity": 0.23, "sociability": 0.32, "arousal": 0.0},
 "scores": {"idle": 0.32, "explore": 0.31, "nap": 0.12, "greet": 0.0, "startle": -0.3},
 "percepts": {"face": true}, "mode": "IDLE", "battery_pct": 85.0}
```

`reason` is `free`, `best`, `margin`, `dwell`, `switch`, `urgent`,
`fallback(<failed choice>)` or `safety`; `errors` lists actions that raised.
`poweroff` and `stop` records close the file.

## Tests

```sh
pip install -e '.[test]'      # or: sudo apt install python3-pytest
python3 -m pytest             # from mind/
```

Everything runs with the real codec and messages. `test_codec.py` checks the
adapters against `protocol/vectors` and that the vendored copies match
`protocol/`. The link tests use an in-memory loopback with a scripted peer:
liveness gating, goal refresh and epoch clearing, query/command retries and
de-dup, reconnect, reboot detection. `test_vbody.py` runs link + client
against the virtual body (every client command) and checks the vbody's
dispatch contract case by case. `test_e2e_cli.py` runs the `kilo` CLI as a
subprocess (`status`, `posture stand`, `param list`, `cal show`) against the
virtual body on a pty. `test_perception.py` and `test_logs.py` drive the
detectors with synthetic traces (approach, walk-by, dropouts, tilt, tap,
pet, pickup, quiet noise) and replay fixture logs (`tests/fixtures/`).
`test_behaviour.py` covers the behaviour engine, drives, selector
hysteresis, personality loading, a simulated seven-minute day with a fake
body and a fast clock, and the runner against the virtual body.
`test_daemon.py` runs the daemon on a real Unix socket
against the virtual body on a pty: every op, hold semantics on disconnect and
lease, streams and their rate, a client that never reads, port
release/reacquire, shutdown, the behaviour hook, and the CLI through the
daemon against direct (same output). `test_settle.py` checks the post-flash
settle against a model of the line (tty core, cdc-acm, HUPCL, a line-coding
glitch), flash verification, `kilo flash` with a fake avrdude direct and
through the daemon, and `kilo monitor --rate`. `test_systemd.py` runs
install.sh (user and `--system` mode) and trim-boot.sh against fake
systemctl/loginctl in a fake `/`. `test_wiring.py` checks the pieces together: socket candidates, the daemon waiting for a missing port and
surviving a replug (a vbody behind a symlink that appears, goes and comes
back), the real behaviour runner under the daemon (behaviour log, posture
goals, body events, clean stop), `kilo run --behaviour --kilolog` end to end
with `kilo monitor --percepts` through it and `kilo log summary|replay` on
the result, a direct `--kilolog` round trip, and wire-byte capture in the
codec and link. `test_hardening.py` holds the regression tests of the second
review: tricks through the daemon (ops, CLI, a killed looping `kilo trick
play`), no motion goal into a rebooting body (the vbody's `boot_delay`
buffers what it hears while it boots), a busy port and a failed verify in
`kilo flash`, a hung runner tripping the watchdog, `--override`, the logs off
the control threads, a cancelled `play()`, the port lease, split-owner idle
latching, the LinkStats race, log pruning. `test_daemon_call.py` pins the `call`
op's allow-list; `test_req_lock.py` measures the link's one request in flight
(printed with `-s`) and the `request` op's timeout cap. `test_gait.py` covers walking:
the spec ranges, the §3d defaults, the vbody's gait state machine
(deterministic: STANCE first, the phase step, the one-period ramp-down,
GAIT_STOPPED once, every refusal, epoch bumps, LIMP, a trick over the gait,
the pose, JOINTS), BodyClient against the vbody (goal bytes, epoch stamp,
refresh, clearing on a fall), the daemon ops and holds, `kilo walk` /
`kilo pose` end to end (also SIGTERM and a P1 body's refusal) and the
renderings; `test_ir.py` the remote's walking. The cross-check's gait case
runs against the firmware's real gait generator (a harness without
SET_GAIT fails it rather than skipping it). The suite takes about
three minutes.

## Background clients over ssh

A `kilo` hold started with `nohup kilo balance on … &` (or any command
without `--for`) from a non-interactive shell ignores Ctrl-C/SIGINT: the
shell starts background jobs with SIGINT ignored. End it with SIGTERM
(`kill -TERM $(cat the.pid)`); the watchdog then lays Kilo down as usual.
Keep the pid in a file rather than `pkill -f` a pattern that matches your
own ssh command line.
